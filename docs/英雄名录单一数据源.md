# 英雄名录单一数据源

> 一句话：**网页端 `src/heroes.js` 是唯一真源，小程序端名录由脚本生成，两端永远一致。**

---

## 一、为什么要有这个

这不是"架构洁癖"，是**已经发生过的真实问题**。

同一批英雄文案，网页与小程序各写了一份。结果分叉了：

| 英雄 | 网站上的说法 | 小程序上的说法 | 问题 |
|---|---|---|---|
| 明彦 | 美男子／红色兔骏马主 | **神箭手**与忠诚伙伴 | ❌ "著名射手"是**哈日吉拉根**的史料职分（Хар Җилң），按错了人 |
| 萨布尔 | 铁臂力士 | 无畏的草原骑士 | ⚠️ 措辞不一致 |
| 哈日吉拉根 | 神箭手 | 骁勇的草原英雄 | ⚠️ 措辞不一致 |
| 赛力汗塔巴格 | 飞毛腿 | 威严坚定的守护者 | ⚠️ 措辞不一致 |

而且**知识库也是从这份数据生成的**，所以同一处错误会扩散到三个地方：
网站图鉴、小程序盲盒页/模型馆、AI 讲解员的回答。

评委把网站与小程序并排看，或者对着我们整理的座次表核对，就会发现。

**根因**：数据分散在多处手写，"改一处忘另一处"是必然结果，不是疏忽。

## 二、结构与用法

```
网页项目 src/heroes.js            ← 唯一真源（含 roster 子对象）
  ├─ id / name / title / description / features / slug / image / poster   （网页用）
  └─ roster: { role, tagText, hidden }                                    （小程序用）
        │
        ├─ node scripts/build-roster.mjs --miniprogram-root <路径>   → 生成小程序端名录
        └─ node scripts/build-knowledge.mjs --cloud-root … --miniprogram-root …
                                                                    → 生成两端语料（含英雄文案）
```

**小程序端 `miniprogram/utils/heroes.js` 是生成物，不要手改**（文件头有明确标记）。

### 常用命令

```powershell
# 网页项目里跑
npm run roster:build     # 生成小程序端名录
npm run roster:check     # 只校验（两端一致 / 没被手改）
npm run test:roster      # 同上，接在 test:all 里
```

改了英雄文案之后的**完整同步流程**（顺序不能反）：

```powershell
# 1. 改 src/heroes.js（唯一真源）
# 2. 重新生成两端语料（英雄文案会进知识库，不同步就会"网站上改了、讲解员还按旧的答"）
node scripts/build-knowledge.mjs `
  --cloud-root D:\WeChatProjects\miniprogram-7\cloudfunctions\ask `
  --miniprogram-root D:\WeChatProjects\miniprogram-7\miniprogram
# 3. 重新生成小程序名录
npm run roster:build
# 4. 构建官网
npm run build
```

## 三、生成与校验都做了什么

**`build-roster.mjs`（生成）** 在写文件前先做真源自检，不通过就**不写**：

- 每尊必须有 `id / name / title / slug / description / features` 与 `roster.role / tagText / hidden`；
- `id`、`slug`、`name` 不得重复；
- 网页端 `type: 'hidden'` 与小程序端 `roster.hidden` 必须表达同一件事；
- **称号不得与其他英雄的史料职分撞车**（"明彦=神箭手"就是这类错误）；
- 生成后逐字节比对：内容没变就不重写（幂等），变了才写。

**`check-roster.mjs`（校验）** 在测试阶段确认：

- 两端条数、`id`、`name` 完全一致；
- 隐藏款标记一致；
- 射手类称号只落在哈日吉拉根一位身上；
- 生成物带"脚本生成"标记，且**与真源重新渲染的结果逐字节一致**（即没人手改）。

> 这两道检查都**验证过会拒绝**：人为把明彦改回"神箭手"、把洪古尔改成"洪格尔"，
> 分别报出"名录内容与真源不一致"与"名字不同"。没有被拒绝过的检查等于没有检查。

## 四、同样的模式还用在哪些地方

| 数据 | 真源 | 产物 | 一致性校验 |
|---|---|---|---|
| 展馆语料（32 段） | 网页 `src/heroes.js` + `index.html` | 云函数 `data/knowledge.js` + 小程序 `data/knowledge.js` | 两端逐字节（`check-narrator.cjs`） |
| **英雄名录** | 网页 `src/heroes.js` | 小程序 `utils/heroes.js` | 两端逐字段（`check-roster.mjs`） |
| 检索引擎 | 云函数 `lib/retrieval.js` | 小程序 `utils/retrieval.js` | 两端逐字节（`preflight.cjs`） |
| 模型资产表 | `models2/` 原始模型 | `dist/models/v/*`（内容哈希） | 构建期校验（`check-assets.mjs`） |

**共同点**：真源唯一、产物生成、构建或测试阶段强制校验。
这套模式是本项目"内容与呈现解耦"的具体实现 —— 也是答辩时可以讲的一条工程化实践。

---

## 五、仍然需要注意的地方

- **不要手改小程序端任何 `data/*.js` 或 `utils/heroes.js`**：它们是生成物，下次生成会被覆盖；
- 云环境 ID（`CLOUD_MODEL_ROOT`）在生成时**从现有文件原样读取**，脚本不自己猜 ——
  换云环境时改配置文件即可，不必动生成脚本；
- 称号的两端表达**允许不同措辞**（网页用"史诗称号"、小程序用"一句话介绍"），
  但必须**指向同一个人**且不与别人的史料职分冲突。过度强求字面一致反而会让小程序文案变生硬。
