## 2. 内容与技术方案详解

### 方案 1：江格尔齐 AI 讲解问答 ★★★

**做什么**：观众打字提问（"洪古尔为什么叫雄狮英雄？""江格尔齐是怎么唱的？"），讲解员只依据站内语料作答，并在回答底部标注依据段落、可点击跳回原文。

**三层实现路径，按风险递增**：

#### Layer 0：语料直塞提示词（半天，赛区选拔赛够用）

语料总量仅 5～8 KB 汉字，**不需要检索、不需要向量、不需要数据库**。全部放进 prompt 即可。

```js
const CORPUS = `
【家园 · 宝木巴】宝木巴是《江格尔》中的理想家园……
【英雄 · 洪古尔】洪古尔是江格尔最信赖的先锋勇士……（本馆文创定位：雄狮英雄）
【传承 · 江格尔齐】"江格尔齐"是对《江格尔》演唱者的称呼……
`;
// 提示词约束（比功能本身更重要）：
// "只能依据资料回答；资料没有的内容必须明确说明'站内资料没有记载'；
//   回答末尾必须标注依据段落标题；不得推测史诗情节。"
```

#### Layer 1：中文 bigram 关键词检索（1～2 天）

语料切段 → 两字滑窗打分（BM25 简化版，约 30 行）→ Top 3 段喂给模型。
**出处标注变得可验证**（命中哪几段就标哪几段）。索引与语料都是一个 JSON，随构建打包。

#### Layer 2：向量语义检索（3～5 天）

- **构建时**（Node 脚本）：语料切段 → 调 embedding API → 写入 `public/knowledge/index.json`
- **运行时**（浏览器）：问题 → 一次 embedding → 余弦相似度 Top 3（毫秒级）

```json
{
  "chunks": [
    {
      "id": "hero-hongguer",
      "section": "heroes",
      "title": "洪古尔 · 雄狮英雄",
      "text": "洪古尔是江格尔最信赖的先锋勇士……",
      "source": "本馆图鉴第 04 位 · 文创演绎",
      "vector": [0.013, -0.041]
    }
  ]
}
```

> ⚠️ 表述准确性："本地向量索引"指的是**相似度计算在浏览器完成**，不是"离线可用"。
> 向量仍由 API 生成，答辩时不要说成"本地模型"。

**是否需要数据库？**

| 需求 | 需要 DB？ | 替代 |
| --- | --- | --- |
| 知识库本身 | ❌ | 一个 JSON 文件 |
| 高频问题榜单（单机演示） | ❌ | `localStorage`，注明"本机统计" |
| 高频问题榜单（全站聚合） | ✅ | 一张事件表即可 |
| 展览数据看板（方案 5） | ✅ | `{session, event, section, ts}` 一张表 |
| **保护 API Key** | ✅ 需要**服务端** | Cloudflare Pages Functions 代理（20 行） |

**结论**：知识库永远不需要数据库；**只有"收集真实观众数据"和"隔离 API Key"两件事需要服务端**。

#### 三条必须提前做的设计（比检索算法重要）

1. **API Key 绝不能进前端**：浏览器里 F12 就能拿走。链路必须是
   `浏览器 → Cloudflare Pages Functions（key 在环境变量）→ 大模型 API`。
2. **断网必须能活**：先查本地关键词检索 → 命中直接返回"本站讲解"（不联网）；
   未命中才调模型 → 失败则回退"网络不可用，先看相关段落"。
   **这样 API 全挂时仍有约 70% 效果，答辩不会哑火。**
3. **合规**：文化类项目最怕编造——"资料里没有记载"要作为正式回答而非失败；
   观众提问需过滤不当内容；高频榜单上线前人工过一遍。

### 方案 2：口传的声音层 ★★

**做什么**：江格尔齐吟诵的节奏展示（波形随吟诵滚动、按段落卡点），或"跟着节奏读"互动。

**红线（不可让步）**：吟诵录音只能用授权版本（传承人授权 / 正规出版 / 非遗机构公开授权素材）。
拿不到授权**不要上真人录音**，改为"节奏可视化 + 文字"，并在页脚写明来源与授权状态。
评委问"音频哪来的"时，**答得清楚比有音频更重要**。

### 方案 3：3D 展厅"读懂细节"纹样标注 ★★★

**做什么**：把镜头拉到袍摆，热区高亮云纹，点击弹出"这一圈纹样是什么、为什么这样画"，与第 05 节纹样解读双向联动。

**为什么值得做**：现在有真实的 150,198 面模型和自研渲染器，却只用来看外观。
把"3D 展示"升级为"3D 讲解"，技术投入直接复用，第 05 节从文字插图变成可操作内容。

**实现**：需要做一次坐标标注工具（在模型 UV / 世界坐标上点选热区），标一次即可复用到 12 个角色。
热区命中判定在 CPU 侧做（射线拾取或屏幕空间距离），不需要改渲染管线。

### 方案 4：内容管理后台 ★★

**做什么**：队友（文案、设计）在浏览器里改章节文字、换图、调人物介绍，导出 JSON 直接进站；带预览、字段校验（标题超长提示）、diff。

**为什么这是技术人员最该交出的东西**：从赛区选拔赛到全国总决赛要反复改文案，每次改都找开发，开发就是瓶颈。
一次投入后内容迭代全组自跑，并能写入"内容与呈现解耦"的工程化加分点。

**联动收益**：同时解决小程序端英雄名录在 3～4 处重复的问题——**单一数据源同时生成 `src/heroes.js` 与 `miniprogram/utils/heroes.js`**。

### 方案 5：展览数据看板 ★★

**统计项**：各章节到达率与停留时长、3D 模型交互率、问答正确率、收藏分布、纹样→模型跳转转化。
**三张图**：观众在哪一节流失、十二英雄谁最受欢迎、八节完整率。

**价值**：从"我做了个网站"变成"我运营了一个有数据的展馆"。
**合规**：只做匿名聚合，不存个人标识——这一点要在答辩时主动说明。

### 方案 6：零等待与离线可看 ★★★（保命项）✅ 已完成

答辩现场网络一定不稳，**这是最常见的翻车点**。

**已实现（2026 年施工）**：

| 能力 | 实现要点 |
|---|---|
| 整站离线可用 | 自写 Service Worker（零依赖）：外壳 + 首屏 4 尊预览模型预缓存（**2.75 MiB**） |
| 导航缓存策略 | HTML **network-first**（内容会改，必须看到新版）+ 离线回落缓存 |
| 静态资源 | 内容哈希资源 **cache-first**（URL 即内容摘要，命中缓存就是最新） |
| 精细模型 | **不预缓存**，只做运行时缓存 + **40 MiB LRU 淘汰**（12 尊近 58 MiB，全预缓存会超站点配额导致整体失败） |
| 离线状态提示 | 断网时顶部出现克制状态条「离线模式 · 正在展示已缓存的内容」，不是弹窗 |
| **现场演示模式** | `?demo=1` 或界面开关：跳过精细模型下载，只加载轻量档（现场网络不确定时直接开） |
| 预缓存清单 | 构建时**内联**进 Service Worker（清单带内容哈希，独立 manifest 文件必然过期） |
| 注入护栏 | 构建期校验清单完整性与 **12 MiB 预算**；误把精细模型塞进预缓存会**直接构建失败** |

**实测（真实浏览器 + 真断网）**：

```
① 首次访问注册并接管            ✅ 刷新后接管，SW 代次 = 当前构建
② 预缓存 24 项 / 全部 200       ✅ 含 4 尊预览模型，2.75 MiB
③ 真断网后重新打开              ✅ 页面完整渲染、状态条出现、3D 展厅正常出模型、取到 519 KiB 预览
④ 省流量模式                    ✅ 等 3 秒零精细模型请求
⑤ 正常模式                      ✅ 自动升级精细档并进入运行时缓存（5.20 MiB）
```

**顺带修掉的 4 个真实缺陷**（都是"离线实测"逼出来的）：

1. **精细模型分支判断顺序错误** → 精细档被当成"永不过期的外壳资源"永久缓存，永不淘汰，看几尊就吃光配额。
2. **写缓存挡在响应之前** → `await cache.put(...)` 让渲染器干等一次完整落盘（4.8 MiB 期间 3D 不显示），且 put 抛错会连响应一起吞掉。
3. **两档都取不到时界面无反馈** → 既不报失败也不给重试入口。
4. **滚回展厅不补调度** → 观众在预览档加载完前滚走，精细档就永远不加载，而界面看起来一切正常。

**答辩口径**：不要只说"我们做了离线"，要说**为什么精细模型不预缓存** ——
"12 尊精细档近 58 MiB，超过浏览器给站点的存储配额，全量预缓存会导致缓存整体写入失败，
结果是一尊都离线不了。所以外壳与首屏预缓存，精细档按需缓存并设 40 MiB 上限淘汰。"

**已知未解**：`scripts/check-progressive.cjs` 里"两档都 404 必须报失败"这条断言在本机产物版上不稳定
（Playwright 的路由拦截在该用例下偶发不生效，与离线链路无关；渲染器侧缺陷已修，见上第 3 条）。

### 方案 7：版本对照阅读器 ★★★ ✅ 已完成

**做什么**：同一段内容做成**不同传承版本的并列对照**。

**为什么这条最击中懂行的评委**：现有章节已写"不同传承与整理本的叙事、称谓和篇幅有所差异"，
但**只有一句免责声明**。这个方案把它从免责声明变成可操作的核心展品，
展示的是对口头文学"变异性"的理解，而不是把史诗当成一份固定文本。

**已实现（2026 年施工）**：新增 `#versions` 一节（「同一个英雄，为什么会有几种名字？」），
用**已核实的材料**做真实对照，而不是编一个漂亮的对比表：

| 部分 | 内容 | 依据 |
|---|---|---|
| A 栏 | 新疆卫拉特传承的**十二勇士宴席座次**（逐条列出，含职分） | 卡尔梅克语言发展中心刊文（Очир Тербатаев 文，依新疆卫拉特版本） |
| B 栏 | 卡尔梅克传承的情形（**刻意不逐条列名**） | 同批材料的另一传承口径 |
| 称谓对照表 | 8 位英雄在两种传承下的写法并列（含原文转写） | 上述两份材料交叉核对 |
| **宝木巴的三重描写** | ①理想国的秩序（12 位英雄／32 位虎将／6000 多名勇士）②乐土的想象（没有衰败、没有死亡）③真实的地点（今新疆塔城地区和布克赛尔蒙古自治县） | 中国关键词项目《江格尔》条目（中国网／国新办英文站同文）+ 中国影像方志《和布克赛尔：英雄史诗〈江格尔〉描绘的乐土》（中国方志网） |
| 变异性说明 | 口耳相传 / 方言与地域 / 整理与翻译三条机制；并补入"研究者指出《江格尔》**没有一个贯穿始终的主角与主情节线索**" | 口传史诗的通行认识 + 上述出处 |

**连带收益（顺带补上一个真实的内容缺口）**：
知识库原本**没有"史诗里到底有多少位英雄"这个数字** —— 而这是观众最常问的问题之一。
现在已把「12 位英雄 / 32 位虎将 / 6000 多名勇士」这组**有出处**的层级数字写进语料：
讲解员对「史诗里有多少位英雄」「有多少勇士」「一共几个人」都能命中并给出具体数字，
**断网时的本地直答也能答**（实测命中 quiz-twelve，分数 21～64）。
语料 3991 → 4064 字，段数不变（32 段）。

**交互取舍**：切换版本只调透明度与边框，**两栏始终同时在屏幕上** ——
对照阅读器的价值就是左右能一眼比较，把另一栏藏起来就失去意义了。
座次表里能对应到图鉴的英雄可点击，直接跳到 3D 展厅看这一尊。

**红线（不可让步）**：宁缺勿编。B 栏不列具体名字，因为**没有核实到**；
每一栏都写明出处，并注明"两种传承材料详略不同"。要补其他整理本或地区版本，
必须一并标注**演唱者、地区与来源**。

**顺带修掉的既有缺陷**：
- 新增内容的文字有 **8 处未达 WCAG AA**（4.00~4.49:1，"刚够不到"肉眼看不出来），
  已全部修到 ≥4.5:1，全站 `contrastFailures` 回到 **0**；
- 装饰性文字（章节序号"壹/贰/叁/肆"、英文小注、箭号）补上 `aria-hidden="true"` ——
  它们本就该被屏幕阅读器忽略，此前只是视觉上低对比、语义上未标注。

**新增工具**：`scripts/check-layout.cjs`（`npm run test:layout`）——
在 3 种视口下量水平溢出、内容溢出父容器、WCAG AA 对比度。
它刻意跳过滤几类**假阳性**：`aria-hidden` 的装饰元素、压在图片/渐变上无法可靠测量的文字
（那类交给 `audit:visual`，它会真实取像素），否则"狼来了"几次之后就没人看了。

**已知未解**：`scripts/check-progressive.cjs` 里"两档都 404 必须报失败"一条在本机产物版上不稳定
（Playwright 路由拦截在该用例偶发不生效，与离线/对照阅读器两条链路无关）。

### 方案 8／9：徽章收集、观众共创 ★（后者留到全国总决赛）

### 方案 10：内容定位 —— 站内搜索与阅读进度 ★★ ✅ 已完成（2026 年施工）

**为什么加这条**：展馆正文已到 **5777 字（约 14 分钟阅读）**、9 个区块、21 个交互控件，
但长页面辅助功能只有"返回顶部" —— 观众想找"谁会射箭""怎么去展馆"只能自己滚。

**做了什么**：

## 3. 扫码 → AR / 空间 3D（重点章节）
> **命名更正**：本章原名"扫码 → VR / 裸眼 3D"。**"裸眼 3D"是错误表述**——它需要光栅/柱状透镜屏硬件，
> 普通手机物理上做不到；"VR"仅指头显沉浸式。为避免材料里出现被评委一问就穿的表述，
> 统一改为 **AR（虚实叠加）** 与 **空间 3D（视差深度感）**。

### 3.0 三个概念的分界（材料与答辩的统一口径）

| 概念 | 一句话定义 | 手机能否实现 | 深度感来源 |
| --- | --- | --- | --- |
| **VR** 虚拟现实 | 把用户放进纯虚拟世界，现实被完全替换 | ⚠️ 需头显（或手机+镜盒双目） | 双目视差 + 头动追踪 |
| **AR** 增强现实 | 把虚拟内容锚定在真实位置，现实仍在 | ✅ 小程序原生支持 | **锚定 + 运动视差 + 遮挡** |
| **裸眼 3D** | 屏幕硬件把不同像素列定向送左右眼 | ❌ **普通手机做不到** | 双目视差（硬件） |

**AR 与裸眼 3D 的效果有重叠，但原理不同**：手机 AR 是**单目**的——左右眼看到相同画面，
立体感来自"你动、物体不动"的锚定感，而非双眼视差。**观众闭上一只眼，AR 的立体感基本不消失**，这就是分界。

**对拍视频的重要影响**：AR 的深度感依赖实时追踪，**录成视频后运动视差消失、立体感大幅衰减**；
陀螺仪空间窗口对视角变化更敏感，**在视频里表现更好**。
→ 结论：**现场演示用 AR；视频素材补一段陀螺仪空间窗口。**

### 3.0.1 让模型"看起来立体"的五个深度线索（按贡献排序）

这是所有空间类方案的设计依据，比选哪条技术路线更重要：

| 深度线索 | 贡献 | 实现方式 | 成本 |
| --- | --- | --- | --- |
| **视线耦合**（用户动，视角跟着变） | ★★★★★ | 陀螺仪 / AR 追踪姿态驱动相机 | 中 |
| **接触阴影**（物体在地面投下影子） | ★★★★☆ | 贴地软阴影面片（径向渐变纹理 + 半透明混合） | **半天，三路通用** |
| **遮挡关系**（被真实物体挡住） | ★★★☆☆ | AR 平面/人体遮挡（xr-frame 能力） | 中 |
| **相对尺度**（与真实参照物比大小） | ★★★☆☆ | 锚定在卡片/展板上，实物即参照 | 低 |
| **光影与景深** | ★★☆☆☆ | 后处理，注意移动端开销 | 低 |

> **只做叠加而不做视线耦合与接触阴影 → 看起来就是一张贴纸。**
> 建议的第一个动作：**先加接触阴影**（半天），三条技术路线同时受益。

### 3.1 平台能力边界（已核实）

**微信小程序侧**：
- ✅ `xr-frame` 提供 3D 渲染、**AR**（平面识别、图像/marker 追踪）能力，见
  [XR-Frame 指南](https://developers.weixin.qq.com/miniprogram/dev/framework/xr-frame/) 与
  [AR 系统文档](https://developers.weixin.qq.com/miniprogram/dev/component/xr-frame/ar/)
- ❌ **不支持 WebXR**（非浏览器环境，无 `navigator.xr`），**无法驱动 VR 头显**
- ⚠️ **AR 在部分安卓机型不受支持**（依赖基础库能力）→ **必须做降级链**
- ⚠️ 取不到摄像头原始帧，自定义 CV 不可行
- ✅ 陀螺仪可用：`wx.onGyroscopeChange` / `wx.onAccelerometerChange`（采样率低于原生，需滤波）

**网页端**：
- ✅ WebXR 可用（`navigator.xr`）：Quest / Pico 自带浏览器可进沉浸式会话
- ✅ `DeviceOrientationEvent` 可用（**iOS 必须由用户手势触发 `requestPermission()`**）
- ⚠️ 微信内置浏览器限制传感器权限，需提供"在浏览器中打开"引导

**结论**：AR 走小程序（原生支持）；VR 头显走网页端 WebXR；两条路**共用同一份 GLB 资产与自研渲染器**。

---

### 3.2 路线 A：AR 虚实叠加 ✅ **推荐主力，先做**

**做什么**：观众扫实物（盲盒卡片、文创包装、展板、景点标识），英雄模型**锚定在实物上**，可环绕、可缩放。

**为什么是主力**：
- 小程序**原生支持**，不需额外硬件 → 评委掏手机就能试
- 与现有业务咬合：盲盒、文创店、包装、展板都是现成的 AR 载体
- **VR 做不到这一点**：VR 里没有"你这张卡片"的概念——VR 脱离实物，AR 绑定实物

**三级降级链（必须实现，不能省）**：

```
扫码 / 扫实物
  ├─ ① AR 模式      设备支持且授权摄像头 → 平面/图像识别 → 英雄锚定实物
  ├─ ② 空间窗口模式  陀螺仪耦合相机 → 英雄悬浮于面前（几乎全机型支持）
  └─ ③ 环绕展示模式  手指拖动 + 双指缩放（保底，即现有能力）
```

**技术缺口（现状核实）**：
- `components/xr-scene/index.js` 是**空模板**：`Page({})` 内所有生命周期为空函数，`index.wxml` 仅一行占位文字
- → **AR 能力目前一行都没实现**，需在 `xr-start` 之外新建 AR 组件

**实现要点**：
- 图像识别用 xr-frame 的 marker / 图片识别（比纯平面识别稳定，室内外都可用）
- 识别目标素材建议用**自家文创卡面**（可控、清晰、无版权纠纷），不要依赖第三方景点照片
- 识别成功后才加载模型（避免无谓流量），并复用现有 `model-glb.js` + `model-renderer.js`
- 加**接触阴影**（见 3.0.1）：这一条对"像不像真的站在桌上"影响最大

---

### 3.3 路线 B：陀螺仪"空间窗口" ✅ **视频效果最强，第二个做**

**原理**：陀螺仪耦合相机，用户转动手机时画面**保持世界固定**，产生强烈运动视差（motion parallax）。

**为什么先做**：
- **约 3 天**，复用现有渲染器，只更换相机姿态来源
- **零硬件依赖**，几乎全机型可用；视频里也出效果（"手机一动，英雄像站在桌上"）
- 是 AR 不可用时的**主要降级路径**

**实现要点**：
- `DeviceOrientationEvent`（网页）/ `wx.onGyroscopeChange`（小程序）→ 四元数 → 相机姿态
- **iOS 必须用户手势触发 `requestPermission()`**，否则静默失败 → 需权限引导页
- 互补滤波抑制抖动；低采样率下做插值
- 必须提供**"回中/校准"按钮**（基准姿态会漂移）

---

### 3.4 路线 C：红蓝立体 ✅（视频补充素材）

后处理通道分离，1～2 元红蓝眼镜即可看到立体。**这是唯一真正给左右眼不同画面的手机方案**。
**代价**：损失色彩保真 → 文化类项目服饰配色会失真，**做成可选开关，默认关闭**，并注明"展示用立体模式"。

---

### 3.5 路线 D：VR 头显 ⚠️（网页端 WebXR，等设备到货后做）

**流程（注意：戴着眼镜没法扫二维码）**：

```
展板二维码 → 手机扫码打开网页（不戴头显）
  ├─ 「放入 VR 眼镜」引导：手机横屏塞进 Cardboard 类镜盒 → 手机双目模式
  └─ 「用头显打开」：在 Quest/Pico 浏览器进 WebXR 沉浸式会话
```

**对 `src/viewer.js` 的改造**：
1. **FBO 离屏渲染**（现在直接渲染进默认帧缓冲，需新增）
2. **双目视图**：左右眼各自投影矩阵（IPD 偏移）与视口，每帧渲染两次
3. **桶形畸变补偿**（Cardboard 镜盒必需，后处理 pass）
4. **头动追踪**：Cardboard 用 `DeviceOrientationEvent`；头显用 `XRFrame.getViewerPose()`
5. **新增第一人称相机 rig**：现有 `yaw/pitch/distance` 是"绕物体旋转"，VR 是"站在场景中"，**不能直接复用**

| 档位 | 内容 | 估算 |
| --- | --- | --- |
| 最小可演示 | 双目分屏 + 陀螺仪头动（无畸变） | 3～5 天 |
| 完整 Cardboard | + 桶形畸变 + 瞳距调节 | +4～5 天 |
| **真头显 WebXR** | + FBO + `navigator.xr` 会话 + 注视交互 | **+1～2 周** |

### 3.6 场景内容本身怎么做（比技术更关键）

现有资产是 12 个**角色模型，没有场景**。三档方案：

| 档位 | 场景方案 | 成本 |
| --- | --- | --- |
| 1 | **角色立于抽象空间**（现有模型 + 草原渐变背景 + 接触阴影） | 1～2 天，零新素材 |
| 2 | **虚幻引擎烘焙的 360° 全景背景** + 角色置身其中 | 3～5 天（见第 4 章） |
| 3 | **多角色同场再现史诗场景** | 2～3 周 + 建模与动画成本（见第 4 章） |

**建议从档位 1 起步**：现在的"人物 + 底座 + 深色展厅"已接近这个效果，
加**接触阴影**和可环绕的空间背景，就能支撑"扫码 → 站在场景里看英雄"的叙事。

**内容红线**：涉及情节再现时**不要臆造具体战役细节**。
定位为**"人物场景陈列"（英雄立于草原/营地）而非"剧情重演"**，并在页面注明艺术演绎。

## 4. 虚幻引擎协同与线下游学

### 4.1 先明确一条技术红线 ⚠️

| 目标平台 | 虚幻引擎能否直接产出 | 现实做法 |
| --- | --- | --- |
| 微信小程序 | ❌ **完全不行** | UE 不支持导出 WebGL/WASM（HTML5 支持已于 2015 年废弃） |
| 普通网页 | ❌ **完全不行** | 同上 |
| Quest / Pico 头显（安卓内核） | ✅ **可以**，打包 Android + OpenXR | **UE 的正道，正好对上 VR 设备** |
| 手机原生 App | ✅ 可以 | 但项目没有 App 端 |

**结论：UE 是 VR 端的引擎，不是 AR / 网页 / 小程序的引擎。**
AR 与展馆仍由 xr-frame + 自研 GLB 渲染器承担。**这条要写进方案，避免承诺做不到的事。**

### 4.2 关键突破口：让 UE「喂」给 AR —— 360° 全景烘焙 ⭐

把 UE 的**画面质量**与你们**实时渲染的能力**接起来：

```
UE 里搭好史诗场景（草原 / 营地 / 宝木巴）
  → 用 Panoramic Capture 插件烘焙成 360° 全景（等距柱状投影）
  → 导出 WebP / JPG（4K 全景约 300～600 KB）
  → 网页 / 小程序里作为天空盒贴上去
  → 现有 GLB 英雄模型「站」在 UE 场景里，实时渲染、可旋转、可 AR 锚定
```

**收益**：
- UE 的**画质**进来了（光照、体积雾、材质都是影视级）
- 你们的**实时交互**保住了（模型可转、可缩放、可 AR 锚定）
- 同一套素材**网页 + 小程序 + VR 三端通吃**（VR 里全景即天空盒）
- 改造成本低：现在 `viewer.js` 的背景就是画在 canvas 上的，加天空盒**约 1 天**

### 4.3 视频路线（小程序唯一的"UE 画质"通道）

把 UE 渲染的 15～30 秒情节动画渲染成视频，小程序用 `video` 组件播放，
播放结束后衔接"可交互英雄模型"。
**这是小程序里唯一能呈现 UE 画质的通道**——因为小程序不支持 UE 运行时。

### 4.4 离线游学场景（项目最大的加分点）

把数字内容放到**江格尔相关文旅景点**作为游览项目，**比"扫码看模型"值钱得多**，
因为它把数字项目变成了**线下可持续运营的产品**。

| 做法 | 技术要求 | 现场表现 |
| --- | --- | --- |
| **图像识别 AR**（最推荐） | 扫景点标识/展板/雕塑 → 出场景 | 稳定，不依赖 GPS，室内外可用 |
| 地理围栏 AR | `wx.getLocation` + 范围判断触发 | 依赖定位精度，室内/林区会漂 |
| 纯扫码 AR | 扫二维码出内容 | 最稳，但缺"现场感" |

**建议：图像识别为主 + 地理围栏为辅**——扫景点标识出该地点的史诗场景；
同时用定位判断"你确实在这里"来解锁专属内容（如集章）。

### 4.5 UE 侧的准备工作与素材管线

1. **模型转换**：`models2/` 是 GLB，UE 需要 FBX / USD → 经 Blender 中转导入
2. **⚠️ 现有模型是静态网格**：要在 UE 里做人物动画，需重新绑定骨骼（**这是个不小的活**，需提前评估）
3. **场景搭建**：草原、营地、蒙古包、旗帜等环境资产（注意免费资源库的授权范围）
4. **烘焙输出**：全景图 / 视频帧序列，注意色调映射与网页配色统一
5. **设备准备**：VR 设备到货后先跑通"打包 Android + OpenXR + 部署"整条链，再谈场景内容

### 4.6 线下游学的合规与安全清单

- 摄像头、定位权限的**用户授权与告知**（小程序隐私协议）
- **不采集**个人生物信息；定位只用于"是否在现场"的布尔判断，不落库
- 景点标识素材的**拍摄与使用授权**（尤其涉及当地居民、私人场所）
- 现场网络：游客用移动网络 → 素材必须走云存储 + 强压缩，**不能假设 Wi-Fi**
- 与景点方的**合作边界**（谁能改内容、谁负责现场物料）

## 5. 建议的执行顺序

时间充裕，按"先立住核心 → 再做高难 → 最后等设备"排：

### 阶段一（1～2 周）：核心内容与保命项

1. **方案 1 Layer 0 + 服务端代理 + 断网回退**（3 天）— 答辩核心演示
2. **方案 7 版本对照阅读器**（2 天）— 内容深度最高性价比
3. **方案 6 离线与降级**（2 天）— 防翻车
4. **修小程序三处硬伤**（半天）：`asset-url.js` 注释不实、删 `xr-scene` 空组件、英雄名录收敛为单一数据源

### 阶段二（2～3 周）：AR 与空间 3D

5. **接触阴影**（半天）— 三条技术路线同时受益，先做
6. **3.3 陀螺仪空间窗口**（3 天）— 复用现有渲染器，视频效果最强
7. **3.2 小程序 AR 扫实物**（5～7 天）— 含三级降级链与机型能力检测
8. **二维码 → 场景入口**（2 天）：二维码贴展板/文创物，扫码进入对应英雄场景
9. **3.4 红蓝立体开关**（2 天）：录视频用

## 7. 风险登记

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **GitHub Pages 部署一直失败** | 若提交 GitHub 地址则无线上站点 | 仓库未开启 Pages，需在 Settings → Pages 选 GitHub Actions；Cloudflare 是独立链路，不受影响 |
| **UE 无法导出到网页/小程序** | 若按"UE 做 AR"规划会白做 | 改为"UE 烘焙全景/视频 + 自研渲染器实时合成"（4.2 / 4.3） |
| 现有模型是静态网格 | UE 里做不了人物动画 | 提前评估骨骼绑定工作量，或先用静态人物 + 运镜/粒子营造氛围 |
| API Key 泄漏 | 额度被刷光 | 必须走服务端代理，key 只存环境变量 |
| 现场无网 | AI 讲解哑火 | 本地检索 + 兜底话术（方案 1 第 2 条） |
| iOS 陀螺仪权限静默失败 | 空间 3D 在 iPhone 上无效 | 用户手势触发 `requestPermission()` + 权限引导页 |
| 部分安卓机型不支持 AR | 现场演示失败 | 三级降级链（3.2） |
| 小程序包体超限 | 无法提交 / 审核被拒 | 立绘与横幅迁云存储 + 配置分包；全景图/视频走云存储不进包 |
| 盲盒/购买类目审核 | 小程序审核被拒 | 提前核对类目与资质，必要时把购买功能与展馆功能分离 |
| 景点素材与居民授权 | 法务与评审风险 | 现场拍摄与使用需授权；标识素材优先自制 |
| 臆造史诗情节 | 文化类项目致命伤 | 定位"人物场景陈列"而非剧情重演，并标注艺术演绎 |
