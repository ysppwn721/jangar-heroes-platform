**B 的根因必须写清楚**（这是我这次审计里最值钱的一条）：

`public/service-worker.js:38-39` 的 `isImmutable()` 用的是**宽松**正则，`/\/models\/v\/[\w-]+-(preview|detail)\.[0-9a-f]{8,}\.glb(\.gz)?$/` —— 它把**精细模型也算成了"不可变资源"**。于是 `fetch` 处理器在 `:128` 先命中 `isImmutable` 分支（写 **SHELL_CACHE**、永久保留），`:144` 的「精细模型 → 运行时缓存 + 40 MiB 限额淘汰」分支**永远不可达**。

后果不是"少一个缓存"，而是三件事同时发生：
- `trimRuntimeCache()`（`:80-99`）成了死代码，**40 MiB 运行时上限完全失效**；
- 精细模型全部堆进外壳缓存（实测已见 `jangar-…-shell` 里躺着 `jiangger-detail.….glb.gz` 5,061,562 字节），12 尊合计 ≈ 57.6 MiB；
- SW 的 `install` 里 `cache.addAll` 是**原子**的（`:51`，注释自称是刻意设计）——外壳缓存涨到 60 MiB 逼近站点配额后，**下一次预缓存会整体失败，新版本 SW 直接不激活**。老观众被永久钉在旧版本上，且毫无提示。

一行正则即可修复，但它现在的状态是"跑过测试、全绿、线上坏着"。

## 3.5 P1：仓库卫生（一笔近 1 GB 的技术债）

实测：

```
$ git count-objects -vH
size: 172.07 MiB          # 松散对象
size-pack: 823.78 MiB     # 打包对象 —— 主要是 incompressible 的二进制模型
$ git ls-files node_modules | Measure-Object -Line
8703                      # 8703 个第三方文件被提交
$ git ls-files models2 | Measure-Object -Line
12                        # 930.2 MB 的高模源，被跟踪
```

三件事叠在一起：

1. **`node_modules/` 被提交**（8703 个文件）。`.gitignore:1` 已经写了 `node_modules/`，但对**已被跟踪的文件无效**——`.gitignore` 只影响未跟踪文件。所以这条 gitignore 是"看起来做了防护、其实没有"。
2. **`models2/` 被跟踪**（930.2 MB）。`.gitignore` 第 12-13 行写着 `models2/` 与 `models.rar`，但 `models2/` 的 12 个文件**早就在索引里**（`git check-ignore -v` 对它无输出 = 未忽略）。README 第 120 行说"工作流使用稀疏检出，不将这两者加入最终网站"——**稀疏检出只影响工作区，不减少 `git fetch` 要传的 823 MiB**。这条说明给了错误的安全感。
3. **同一批模型在仓库里存了三档**：`models2/jiangger.glb` 87,562,740 B（源）→ `models/jiangger.glb` 9,164,928 B → `public/models/jiangger.glb` 7,167,696 B → `public/models/preview/jiangger.glb` 593,624 B。后两档已经够构建用（`build.mjs` 只读 `public/models/`），**`models/` 这一档（97.3 MB）没有任何脚本读它**。

**建议（按代价从低到高）**：

| 做法 | 代价 | 效果 |
| --- | --- | --- |
| `git rm -r --cached node_modules models` + 提交 | 一次性，10 分钟 | 索引瘦身，未来 clone 不再拉这 8703 个文件；`.gitignore` 从此真正生效 |
| `models2/` 迁出仓库（移到 `D:\` 本地或对象存储），仓库里只留 `public/models/` | 半小时 + 确认构建只依赖 `public/` | 未来 clone 从 ~1 GB 降到 ~110 MB |
| 若必须保留历史（授权/审计），用 `git filter-repo --path models2 --path node_modules --invert-paths` 重写历史 | 半天，会改写所有 commit hash、需要 force push | `.git` 从 997 MB 降到 ~120 MB |

坦白说第三条有争议：如果赛区选拔赛材料里已经引用了旧 commit hash，重写历史会造成材料与实际不一致。**我的建议是先做前两条（对未来有效），把第三条留到全国总决赛前、且确认没有材料引用旧 hash 之后再做。**

## 4.5 渲染器正确性深挖（我原先怀疑、逐项验算+实测后的结论）

> 这一节的价值一半在"**其实没问题**"——验算过的结论要写下来，否则下一个人还得再怀疑一遍。

### ✅ 验算通过（我原先怀疑，结论是干净）

| 我怀疑的 | 验算方式 | 结论 |
| --- | --- | --- |
| `perspective()`（`src/viewer.js:79-82`）的列主序排列可能不对 | 与数学定义逐项对比（`f/aspect, f, (far+near)/(near-far), -1, 2·far·near/(near-far)`） | **完全一致**，`m[11] = -1`（w 系数正确） |
| `lookAt()`（`:83-89`）可能把 z 轴方向搞反 | 用正确的列主序取值重算：`原点 → (0,0,-5)`、`eye 本身 → (0,0,0)`、相机前方一点 → z 为负 | **正确**。x 轴取 `(z2, 0, -z0)`、y 轴取 `z × x`，是标准构造 |
| `lookAt` 里 `xLength = hypot(z[2], z[0])` 会不会除零 | pitch 被 clamp 在 ±1.15 rad（`:307`、`:357`、`:373`），`cos(1.15) = 0.4085`；只有 pitch 真的到 ±π/2 才会 `xLength = 0` | **不会触发**。0.4085 的余量很安全 |
| 非 2 的幂贴图在 WebGL1 上 `generateMipmap` 会报 INVALID_OPERATION | 在真实浏览器里对 1536²/768²/2048²/1024²/512² 逐一调 `generateMipmap` 并读 `getError()` | **判定正确**。`src/viewer.js:263` 的 `webgl2 \|\| (powerOfTwo(w) && powerOfTwo(h))` 恰好把 NPOT 挡在 WebGL1 之外，无报错 |

### 🟡 真实问题：显存预算**从未生效**（注释宣称的机制不存在）

`src/viewer.js:189-202` 的注释写：

> 这里估算本机可承受的贴图**总量**，**超预算时降低贴图尺寸再上传**

但 `:235` 的实际实现是**逐张贴图**判断：

```js
const perTexture = Math.max(4096, textureBudget() * 1048576);
while (bitmap.width * bitmap.height * 4 * scale * scale > perTexture && scale > 0.25) scale /= 2;
```

`textureBudget()` 返回的是 **24 / 48 / 128（MiB）**，乘 1048576 后是字节——**量纲没写错**（我原先怀疑的量纲问题不成立，那个 `4096` 是 4096 **字节** = 一张 32×32 RGBA 的下限，实际不起作用）。

问题在于**它是"总量"预算，却被拿去和"单张"比**：

| 模型 | 贴图（实测自 GLB） | 合计 | 含 mipmap | 单张最大 | 在 24 MiB 预算下会不会缩放 |
| --- | --- | --- | --- | --- | --- |
| jiangger | 2048² + 2048² + 1024² | 48.0 MiB | 64.0 MiB | 16.0 MiB | **不会**（16 < 24） |
| sanala 等 11 尊 | 1536² + 768² + 768² | 13.5 MiB | 18.0 MiB | 9.0 MiB | **不会**（9 < 24） |

也就是说：**逐张都"没超"，合计早就超了**。而最严的一档预算（`MAX_TEXTURE_SIZE < 2048` → 24 MiB，`:200`）本意正是保护老机型，偏偏在这条路径上完全没有约束力。

实际风险要如实说：**不是崩溃级**。`present()`（`:388-394`）会释放上一尊，缓存上限 3 尊（`:392`），换尊瞬间的峰值是"旧的还没放 + 新的已上传"≈ 112 MiB，16 GB 级别的机器扛得住。所以这条是**"宣称的保护不存在"**，不是"线上正在崩"——但它是一颗定时炸弹：只要有人把贴图加到 4096²，或把缓存上限从 3 调大，就会真的崩，而且**注释会告诉维护者"放心，有预算保护"**。

**修法（两行）**：把逐张判断改成**先累计、再逐张降**，并按 mipmap 计 ×4/3。

### 🟡 同一个函数被放进了循环（小毛病，但不是纯洁癖）

`textureBudget()`（`:193-202`）内部每次都要 `gl.getParameter(MAX_TEXTURE_SIZE)`、`gl.getParameter(RENDERER)`、`matchMedia(...)` 各一次，还要对 12+ 字符的渲染器字符串跑一遍正则。而它被写在 `while` 的条件里（`:237`）——一张 4096² 的贴图会走 5 次循环 = **5 次 `getParameter` + 5 次正则 + 5 次 `matchMedia`**。`getParameter` 是同步 GL 查询，属于"能省就省"那一类。抽到循环外面即可。

### 🟢 两个小项

- **死变量**：`src/viewer.js:250` 的 `const powerOfTwo = ...` 在 `upload()` 里声明后**从未使用**。真正用它的是 `:262`（`applyTextureFilter` 内部，另有一份正确实现）。看起来是重构时把 mipmap 判定移进 `applyTextureFilter` 之后忘了删除。
- **`analyze-models.mjs` 的 GPU 估算与 WebGL1 解耦**：它用 `gpuWithMips = w*h*4*4/3` 无条件按"有 mipmap"算（`scripts/analyze-models.mjs:38`）。但 WebGL1 下 1536² 与 768²（11 尊模型）**不会**生成 mipmap，所以那些行的 `GPUtex` 被高估 33%。`audit:models` 的输出目前会让人以为显存占用比实际高。
- **`powerPreference: 'low-power'`**（`:147`）：本机实测 `ANGLE (Intel, Intel UHD Graphics…)`、WebGL2、`MAX_TEXTURE_SIZE=16384`、精细档正常、画布 712×543。在集显机器上这个选择没问题；有独显的演示机则被主动降级。建议按 `gl.getParameter(gl.RENDERER)` 探测后决定（§4 第 4 条）。
